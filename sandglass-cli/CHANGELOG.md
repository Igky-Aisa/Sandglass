# Changelog

## [Unreleased]

## [0.10.0] - 2026-08-14

### Fixed

- **A `CLINE: STOP` safety annotation was being parsed as the routing command it forbade.** `_external_defaults` treated any `CLINE:`/`EXTERNAL:` value as a routing target, with no concept of negation. A queue used `**CLINE: STOP** — OPUS tier: money path, concurrency, crash recovery... Claude only` as a plain-English warning to keep a block on Claude; Sandglass read it as "route externally, tier=STOP", and since "STOP" isn't a recognised tier, fell through to the default external provider anyway — sending `model: opus` blocks to DeepSeek, where "opus" resolved through DeepSeek's own tier map to `deepseek-v4-pro`. Confirmed live: an unattended order-placement block had already run this way and billed $7.55; a crash-resume/money-path block was mid-run on DeepSeek when caught, with 8 more `CLINE: STOP` blocks still queued behind it. `_CLINE_NEGATIONS` (`stop`, `no`, `none`, `off`, `never`, `claude-only`, etc.) is now checked before any provider resolution, so a negation never routes.

### Added

- **Every stop reason now pushes exactly one ntfy notification, including under `--once`.** Previously notifications for quota and no-artifact stops were sent inline from `execute_queue`, but a generic error, a left-in-place stop, and a clean full completion were only ever sent from `run_with_auto_resume`'s post-hoc wrapper — a path `--once` never reaches, so those three cases notified nobody under it. Fixed by moving every stop-reason notification to fire inline in `execute_queue`, at the point each reason is actually detected, and deleting the now-redundant wrapper logic in `run_with_auto_resume`. That same tracing also caught a real, pre-existing **double notification**: a no-artifact stop was sent once by `execute_queue` and a second time by the wrapper under the default (non-`--once`) mode — confirmed with a test asserting exactly one send, not two, before the fix existed.
- **5% prompt-throughput milestones**, pushed via the same ntfy pipe as every completed block in a markdown-sourced queue lands, and **`master_plan/Progress.md`'s "Prompt throughput" section kept live** as they do — the same done/remaining/total/percent definition CLAUDE.md's "check progress" trigger already uses (live `====` blocks in `future_prompts.md`, `## `-headed entries in `prompt_history.md`), computed automatically per block rather than only when a human runs that trigger by hand. New `prompt_source.throughput()` does the counting, fence-aware so a completion entry that legitimately quotes its own block text inside a fenced code block is never mistaken for a second completion record — the exact miscounting bug `templates/prompt_tools/count_blocks.py`'s own docstring documents costing four days on a real project. New `project_docs.update_progress_throughput()` overwrites only the three throughput bullet lines, matched by an exact regex, and touches nothing else in the file — in particular never the qualitative "Against the main idea" phase judgment above it, which is a call only a human or an agent reading the architecture doc can make. Milestones only move forward: the highest one already pushed persists in `.sandglass/progress_notify.json`, so a restarted run doesn't re-announce 5%, 10%, 15%... from scratch, and several blocks landing inside the same band notify once.

### Fixed

- **A refusal was being archived as a success, and the damage compounded every run.** The most destructive bug found so far, and it inverted the artifact gate on exactly the runs that gate exists to catch. A project's `CLAUDE.md` typically mandates a `master_plan/work_log.md` entry for *every* task — including a task that cannot do its work and correctly says so. The gate ignored only `.sandglass/`, so that mandated log write counted as a changed file, the block passed as productive, and it was cut from `future_prompts.md` and archived into `prompt_history.md` as executed having built nothing. Confirmed live in a 30-block run: block `P6.08`, whose own saved response opens "**P6.08 is BLOCKED. I made no code changes**", was reported `✅ Done`, removed from the queue, cut from the source and filed in the history — alongside a work-log entry at `work_log.md:6007` that was the very write which fooled the gate. That project's `progress.md` separately records `P1.17`, `P2.06` and `P2.07` being lost and restored by hand earlier: same mechanism. **It is self-reinforcing** — each refusal deletes a real block from the plan and adds a false "done" to the history, so the blocks that depended on it later arrive to find their dependency missing, refuse in turn, and are archived the same way. The queue drifts further from the repository with every run, which is why it presents as "the same block always stops the flow". Four named files are now excluded from the fingerprint: `master_plan/work_log.md`, `master_plan/progress.md`, `prompt_tools/prompt_history.md`, `prompt_tools/future_prompts.md` — a file the process itself mandates cannot be evidence that the process produced anything. Deliberately **four filenames, not `master_plan/` wholesale**: that directory also holds architecture docs, and a block whose whole job is editing one has genuinely produced its deliverable (pinned by its own test). Blocks already orphaned this way are a data problem in the affected project, not something this fix repairs — they must be audited against the repository and restored by hand.
- **A block with no session to resume was never asked why it changed nothing, so the recovery skipped the queues that stop most.** `_ask_why_nothing_changed` bailed out whenever there was no conversation to continue — but externally-routed blocks run cold *by design*, and a queue whose early blocks are all external never opens a chain at all. Observed on the same 30-block run: 28 blocks routed to DeepSeek, every block logged `session=ephemeral`, and the stop was reported with no verdict. A cold block now gets the same DONE/BLOCKED/NOOP question with the evidence attached — its own block text and the response it gave — since it cannot remember an exchange that happened in another session. That question never opens a session of its own: it would become the chain the next block joins, handing it a classification exchange as its entire project history.
- **The project-state brief has never actually fired for the default queue layout.** `execute_prompt` builds it via `project_docs.build_brief(cwd=ExecutionEngine._project_dir(prompt))`, and `_project_dir` computed the brief's target directory as a single `dirname()` on the queue source — landing on `prompt_tools/` itself, which never contains `master_plan/` (a *sibling* of `prompt_tools/`, not its parent). Confirmed empirically: `build_brief` returned `None` for the exact default layout (`prompt_tools/future_prompts.md`) every time. This meant every markdown-sourced block was silently paying the full cost of re-reading `work_log.md` in whatever way its own headless run chose to — the cost the brief exists to eliminate, undetected because nothing tested the interaction between a markdown-sourced prompt and brief injection. `_project_dir` now walks up from the source file's directory (bounded to a few levels) looking for a `master_plan/` sibling, rather than assuming one `dirname()` lands on it. The artifact gate escaped the same bug by accident, not by design: it shells out to `git`, which resolves its own repo root via `git rev-parse --show-toplevel` regardless of the `cwd` it's given — confirmed this still holds and was deliberately left untouched, since it is safety-critical code already functioning correctly and a separate, higher-stakes change from anything else here.

- **A block can be sent to a non-Anthropic provider, so mechanical work stops competing with Opus work for the same quota.** New `sandglass/providers.py` routes a marked block through DeepSeek's Anthropic-compatible endpoint (`https://api.deepseek.com/anthropic`) using the same `claude` CLI — tools, artifact gate and history cut all unchanged, because file edits and shell commands never leave the machine. Naming the model is enough: `model: deepseek-pro` (or `--model deepseek-pro`) routes on its own, because naming a vendor's model *is* choosing that vendor and making someone say it twice is a rule they will forget on the one block where it matters. A `**CLINE: pro**` marker and `provider: deepseek` front matter mean the same thing, the latter winning over both. Inference fires on the **vendor prefix only** (`deepseek-…`), never on the tier map — that map holds bare words like `pro`, `opus` and `haiku` so they can be resolved once a provider is chosen, and matching on it would send an ordinary `model: opus` block to DeepSeek. `sandglass providers set deepseek --key …` stores the key in `~/.sandglass/providers.json` (or `$DEEPSEEK_API_KEY`), outside the repo for the same reason account tokens are; `sandglass providers list` shows what is configured. This is a different trade from the account pool, not a replacement: the pool spreads a queue across subscriptions you already pay a flat rate for — free at the margin but finite — where an external provider is metered and never free, but doesn't consume quota you were saving for work that actually needs Opus.
- **Routing is opt-in per block and can never be inferred.** An unmarked block never leaves Anthropic, whatever is configured, because routing sends the prompt, the injected project brief and every file the agent reads to that vendor under *their* retention policy — a disclosure only the block's author can consent to. In particular `**TIER: CHEAP — EXTERNAL-OK**` does **not** route: it predates this feature and sits on blocks written long before it existed, where "EXTERNAL-OK" is the author granting permission and `CLINE:` is exercising it. Conflating the two would have retroactively sent a pile of old blocks to a third party on the strength of a comment nobody wrote with that consequence in mind. `--no-external` forces everything back onto Anthropic for a run, and `execute` prints how many blocks are marked before the first one is sent — the last moment Ctrl-C is still free.
- **`CLAUDE_CODE_OAUTH_TOKEN` is stripped from an external subprocess.** It is a live subscription credential, and leaving it set while `ANTHROPIC_BASE_URL` points elsewhere would transmit it to that third party as a bearer token with nothing in the output looking wrong. It is the single load-bearing line in the module and has its own test.
- **A routed block runs cold, outside the chain, in both directions.** Resuming would replay the whole accumulated Claude conversation — every file the queue has read so far — to a third-party endpoint, which is a far larger disclosure than the marker asks for; letting the external turn *into* the chain would hand later Claude blocks another vendor's output as their own history. It costs a cold start, which is precisely what the block is being routed away from Anthropic to make cheap.
- **External spend is reported as an estimate and never charged to a Claude account.** The CLI prices every run off Anthropic's table because that is the only table it has, so a routed block's `cost_usd` is an order-of-magnitude stand-in rather than a bill; the per-block line and the run summary both say so, and `AccountPool.record_usage` skips it — folding it in would inflate an account's apparent burn *and* hide the third-party spend. A rate limit from an external endpoint likewise no longer rotates Claude accounts: someone else's 429 says nothing about a subscription, and acting on it would park a healthy account for an hour.
- Missing key, unknown provider, or `--no-external`: the block runs on Claude with a warning rather than failing. A routing marker states a preference about cost, not a correctness requirement, so stopping a queue over a missing config line would be the worse failure — and the fallback direction is always *toward* Anthropic, never silently outward. The block's `deepseek-…` model name is swapped for the run default in the same step: forwarding it would ask Claude for a model that does not exist there, turning a missing config line into a hard failure on every marked block — precisely what the fallback exists to prevent. The substitution is printed, never silent.
- **A pool of your own Claude subscriptions, rotated on quota exhaustion instead of waited out.** A single subscription's quota is a hard ceiling on an unattended run: hit it at 2am and the auto-resume logic does the right thing — sleeps until the window refreshes — but the queue spends most of the night idle. Someone holding more than one subscription can carry on under the next one. New `sandglass/accounts.py` loads `~/.sandglass/accounts.json` (override with `SANDGLASS_ACCOUNTS`); `--accounts auto|rotate|off` on `execute`, defaulting to `auto`, which rotates when that file exists and is a no-op when it doesn't — so nothing changes for anyone who never writes one. On `QuotaExceededError` the engine marks the current account spent (recording the CLI's own `resetsAt`, so it knows *when* it comes back, not just that it's gone), advances, and **retries the same block** — a quota hit interrupts work that was never done, so re-sending it is the entire point. Only when every account is spent does the error reach the existing wait path, which then sleeps until the **earliest** account refreshes rather than the one that happened to fail last; on waking, any account whose window has rolled over re-enters the rotation. **These must be accounts you hold yourself** — Anthropic's Consumer Terms forbid sharing credentials or making an account available to anyone else, and the number of subscriptions is not what that clause is about.
- **Exhaustion times survive the process.** Each account's expected refresh is written to `.sandglass/accounts_state.json` (names and epochs only — never a token) as it is learned, and re-applied on startup. Without it a restarted or crashed run sees a full pool, starts at the first account, and spends a real block rediscovering a quota the previous process had already found — once per dead account, every restart. On load, the pool also advances past any account still inside its window, so the run begins on one that actually has quota. Times already in the past are ignored, so a stale file self-clears rather than pinning an account off.
- Tokens are injected per-subprocess via `CLAUDE_CODE_OAUTH_TOKEN` (mint them with `claude setup-token`), which leaves the machine's own interactive `claude` login completely untouched — you can still use Claude Code by hand under a different account while a rotated batch runs. `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` are **stripped** from that environment: either one outranks the subscription token and would silently bill pay-per-token API credits instead, defeating the point of the pool and announcing itself only on an invoice.
- **`sandglass accounts`** lists the pool, checks every token, and shows which accounts have quota now and when the spent ones come back — free, and the way to confirm a freshly written `accounts.json` before trusting it to an overnight run.
- **Token validity cannot be checked offline, and Sandglass no longer pretends it can.** An earlier draft of this feature inferred validity from `claude auth status` returning an email. That was wrong in the worst direction — it warned that *every* token was broken, including working ones, because `auth status` performs no validation at all: it reports `loggedIn: true` for the literal string `x`, and never carries an email under `oauth_token` auth since the email comes from the keychain profile an env-var token has no equivalent of. Startup now checks only what is genuinely checkable for free — a token that is empty, truncated, whitespace-wrapped, or still the ellipsis placeholder from the README, plus the same token pasted under two names — and makes no claim about validity. Real verification is `sandglass accounts --probe`, which spends one minimal request per account and is the only thing that can tell a working token from an expired one. Deliberately no prefix is asserted: the issuing format is Claude Code's to change, and rejecting good tokens is worse than accepting bad ones the probe would catch anyway.
- The probe runs from an empty temporary directory so the project's `CLAUDE.md` is not auto-discovered — measured at ~23,000 billed tokens in this repo, which would make checking three tokens cost more than the blocks it protects.
- **Confirmed empirically that this is the subscription path, not the API.** With `CLAUDE_CODE_OAUTH_TOKEN` set, `claude auth status` reports `authMethod: oauth_token` / `apiProvider: firstParty`; a plain interactive login reports `authMethod: claude.ai` / `apiProvider: firstParty`. Same provider, same subscription billing — the variable that switches to pay-per-token is `ANTHROPIC_API_KEY`, and the docs are explicit that under `-p` it always wins when present, which is exactly why it is stripped. How the account signs in to claude.ai (Google SSO, email) is irrelevant: the token represents the account, not the identity provider.
- **A credential never reaches anywhere a block can read it.** This is why the accounts file lives outside the project by default. Queued blocks run with `bypassPermissions` in the project tree and their responses are persisted verbatim to `.sandglass/responses/`, so a token stored inside the repo is one incurious `cat` away from being written into a file that outlives the run — and this is not hypothetical: a block in a live run was observed reading `.sandglass/last_run.json` unprompted, to reason about its own environment. `Account.__repr__` redacts, so a token cannot surface in a traceback or a debugger's locals either, and the run report carries per-account **names, block counts, tokens and cost — never the token**.
- The rotation deliberately does **not** touch sessions. Transcripts are local files that `--resume` replays under any credential, so a chained queue keeps its context across a switch (confirmed against five days of doing this by hand). What is per-account is Anthropic's *server-side* prompt cache: the first block under a new account pays a cache write rather than a read. That cost is why accounts are drained one at a time in file order instead of balanced across — one deeply-cached account beats three shallowly-cached ones.
- `sandglass why` and the end-of-run summary print the per-account split when a run crossed accounts, so a rotated run reads as "what did each one actually do" rather than one merged total that hides the crossing entirely.

### Fixed

- **A run no longer crashes when a block modifies the queue while it is working.** Observed live and expensive: a 20-minute block completed, having cost $10.21 and 14.1M tokens, and the engine then died with `IndexError: Index 1 out of range (1-0)` removing it from the queue — because `.sandglass/queue.json` had been emptied at 11:41, mid-run, and the removal ran at 11:44. The completed work was archived but the block was never cut from `future_prompts.md`, so it would have re-run and cost the same again. Root cause is structural: `.sandglass/` lives inside the project directory, which is exactly where queued blocks run with `bypassPermissions` — and blocks reliably find those files and reason about them (an earlier block in the same project wrote advice about "the Sandglass CLI's generated mirror" and re-syncing it).
- Removal is no longer positional. **It is also not by id alone** — ids are sequence numbers assigned on insert, not identities, so clearing the queue and adding anything else makes it `001` again and an id-only match would have deleted an unrelated block. `remove_prompt_entry` matches id *and* text, and returns `None` instead of raising when the entry is already gone: by that point the work is done and the queue entry is bookkeeping, not something worth failing a run over. Caught by the regression test rather than in production, which is the only reason this note is short.
- **Blocks are now told that `.sandglass/` is not theirs.** The injected project brief says the directory is the runner's own bookkeeping, must not be written to, and that a `running` entry in `last_run.json` is *this* run rather than a competing process holding a lock — the exact misreading that made an earlier block refuse to write anything at all.


- **A chained session is no longer rejoined once its cache has expired, and its clock is measured from last use.** Two faults in one. The idle cutoff was 24 hours, but the prompt cache lives an hour at most: resume inside that window and the whole conversation is a cache *read* at ~0.1x, resume after it and the same conversation is a cache *write* at 1.25–2x — of the accumulated conversation, which grows with every block, where a cold start's prefix does not. Measured on a real run: resuming a session hours old billed **741k cache-write tokens ($4.92) to produce 1,908 tokens of output.** The cutoff is now one hour. Separately, the timestamp was written only when the chain *opened* and never refreshed, so age meant "time since the chain started" — an eight-hour batch would have thrown away a session it used seconds ago, while an overnight gap on a young chain would have rejoined a stone-cold one. It now tracks last use, which is what actually decides whether the cache is warm.
- **A prompt beginning with a dash killed the batch: `error: unknown option '---…'`.** Sandglass passed the prompt as `-p <text>`, but `-p/--print` is a **boolean flag** and the prompt is a positional argument (`claude [options] [prompt]`) — so the text simply landed in argv unprotected, and the CLI's option parser read any leading `-` as a flag. This went unnoticed until session chaining shipped, because the chain turn separator starts with a `---` markdown rule: the first block of a chained queue ran fine and the **second one always died**, taking the rest of the queue with it (seen live: 34 blocks, block 1 completed, block 2 failed at 1.4s). It was never specific to the separator — a block opening with a `- ` bullet or a `--flag` would have done the same. The prompt is now passed last, behind `--`, which ends option parsing and makes every prompt shape safe.
- **Sandglass no longer names Claude Code sessions itself — and a stale session can no longer wedge a queue permanently.** Found in a live run: `Error: Session ID 679430b1… is already in use.` on block 1 of 34, repeating on every subsequent attempt. Two compounding faults. First, the chained session id was generated by Sandglass and passed as `--session-id`, which forces it to guess whether the CLI has already created that session; guess wrong and every retry fails identically, and because the id is only marked "started" after a *successful* send, an attempt that created the session and then died left a `started: false` record pointing at a live session — an unrecoverable loop with no way for the queue to move. Second, the recovery path for exactly this error existed but was unreachable: a rejected session makes `claude` print to **stderr and exit without emitting a `result` event**, and only the result-event branch checked for recoverable session errors. Fixed at the root — Sandglass never passes `--session-id`, it lets the CLI assign one and reads it back off the response (`Response.session_id`), so the recorded session is always one that demonstrably exists. Both failure shapes now reach the same recovery, which falls back to a fresh session rather than stopping the batch. Recovering from a wedged state needs nothing but the upgrade; deleting `.sandglass/run_state.json` also clears it.
- **A quota hit part-way through a block now records the session it was using.** `QuotaExceededError` carries `session_id`, and the engine stores it before the error propagates. Without this the retry after a quota wait started cold and re-derived everything the interrupted attempt had already worked out — precisely the failure chaining exists to prevent.
- **Token accounting counted a fraction of what a run actually cost.** `claude_client` summed `input_tokens + output_tokens`, but on a cached prompt the API reports `input_tokens` as the *uncached remainder only* — the cache buckets, which are usually the dominant term, were dropped on the floor. Measured with a do-nothing prompt (`"Reply with exactly: OK"`) in a project with a large `CLAUDE.md`: the CLI reported `input 10 / cache_creation 11,186 / cache_read 12,549 / output 43`, i.e. **23,788 tokens billed and $0.024 spent** — and Sandglass recorded **53**. Every historical figure the tool has ever printed is therefore a floor, not a total, and for small runs it is off by a factor of ~450. `Response` now carries all four buckets plus `total_cost_usd`, `execute` prints cost and the cache read/write split, and `sandglass history` shows both per prompt. This is listed first because nothing else here is measurable without it.
- **History rows written before this change are marked, not silently mixed in.** They carry `accounting: 1`; new rows carry `2`. `sandglass history` flags the old ones with `*` and excludes them from its totals — averaging a schema-1 undercount together with a schema-2 real number would produce a figure that is wrong in a new and less obvious way.

### Fixed (previously)

- **A prompt that produces no work product is no longer cut from its queue source.** This is the most damaging bug Sandglass has had. The cut-on-completion step is a *lock* — it removes a block from `future_prompts.md` and archives it into `prompt_history.md` so no other runner executes it twice — but it fired on "the model returned a response", not on "the model produced the artifact". A run that reads the repo, correctly concludes it *cannot* build the block (an unbuilt dependency, a missing foundation), and says so in prose returns exactly like one that wrote a thousand lines. Both got cut, and the cut destroys the only copy of the block text, so the phase becomes undeliverable and no runner ever picks it up again. In the project where this surfaced, **twelve blocks** were archived as executed having landed zero code; two of them (`.sandglass/responses/response_041.json`, `response_042.json`) are verbatim refusals to proceed. `execute_queue()` now fingerprints the git working tree before and after each markdown-sourced prompt and, when nothing changed, refuses the cut, leaves the prompt at the front of the queue and its block in the source file, and **stops the run** — a refusal almost always means a missing dependency, and the blocks behind it depend on the one that just refused, so continuing burns them too (exactly what happened: P4.03 refused, then P5.01, then P5.03). New `sandglass/workspace.py`; `--no-require-artifact` restores the old permissive behaviour for queues of genuinely read-only prompts.
- The check deliberately measures the **working tree**, not the response text. Classifying prose as a refusal is a losing game — models phrase it a hundred ways, and a confident misclassification is worse than none. "Did any file change?" is a fact.
- Three things it had to get right, each of which was a bug in the first draft and now has a regression test: **Sandglass's own `.sandglass/` writes are excluded** (a response JSON is written for every prompt, so counting it would have made the gate a permanent no-op); **an already-untracked file that is edited again registers** (`git status --porcelain` names an untracked file but not its contents, so a stat stamp is folded in — without it the gate would block real work); and the measurement is **anchored at the queue source's own repo**, not the process CWD.
- Fails **open** when it cannot measure — outside a git repo, or with git unavailable, the run behaves exactly as before. Prompts added with `queue add` are never gated: they have no block to protect.

### Added

- **A block that changes no file is now asked what happened, instead of ending the batch (`--on-refusal ask`, the default).** Three very different situations look identical from outside — the work was **already done**, the block is **blocked** on something unbuilt, or it genuinely **needed no file change** — and only the run that just refused already knows which. It gets one short follow-up turn in the session it just used (a cache read of an already-warm context, cents against the price of a whole block) asking for `VERDICT: DONE | BLOCKED | NOOP` plus one line of why. `DONE`/`NOOP` keep the queue moving; `BLOCKED` stops as before but now **names the missing dependency** in the console, in `sandglass why`, and in the ntfy push. Anything unparseable stops: continuing is the optimistic branch and has to be earned. `--on-refusal stop` restores the old always-stop behaviour.
  - **It never cuts a block on the model's word.** A left-in-place block stays in the queue *and* in its source file — the cut destroys the only copy of the block text, which is exactly what the artifact gate exists to prevent, and a self-report is not evidence. The run ends as `left_in_place` rather than "complete", listing each block so nothing is quietly assumed finished.
  - Cutting now targets **the block that actually ran**, matched by its own heading, rather than whichever block sits first in the file. Those are the same block only while nothing is ever skipped, and cutting the wrong one destroys unbuilt work.
- **Blocks another runner already executed are dropped before they are sent.** `queue.json` and `future_prompts.md` are two copies of the same intent and they drift — an interactive session executes a block and cuts it, or a run dies between the cut and the queue update. Sandglass then re-dispatched finished work: measured live at **$4.92 and a stopped batch** to be told P6.04 was already complete. A free pre-flight now drops such a block, requiring **positive evidence** (gone from the source file *and* present in the sibling history file) because the risk is asymmetric: re-running finished work costs money, but skipping unfinished work silently loses a deliverable. `--no-skip-executed` disables it.
- **`sandglass why` — every run now records why it stopped, and says so.** Asked for after a real run stopped overnight and the only copy of the answer was in a terminal nobody was looking at. A queue run is unattended by design, so the moment it ends is almost never a moment anyone is watching: the explanation scrolls away, the terminal gets closed, the laptop sleeps, and what is left on disk (`history.json`, file timestamps) supports guessing, not knowing. Every run now writes `.sandglass/last_run.json` as it goes — what it is doing right now, and the moment it ends, why — and prints a **"Why it stopped"** block with the cause, the CLI's own error text **verbatim** (a quota message carries its reset time; a paraphrase loses it), and the one thing to do next. `sandglass why` prints it back at any time.
  - It covers the endings a run cannot narrate itself: **Ctrl-C** and an **unhandled crash** are recorded by the CLI on the run's behalf, and a **quota wait** reports as `waiting`, not `stopped`, for as long as it is actually sleeping — "why is nothing happening" is a fair question to ask in the middle of a three-hour wait.
  - **The case it was built for is the run that never got to write anything.** A process killed from outside — closed terminal, sleeping machine — leaves its record stuck at `running`. Since the record carries a PID, that combination *is* the answer: Sandglass reports the run as killed, names the prompt that was in flight, and states plainly that it was neither a quota limit nor a failure of the prompt, which are the two things a reader would otherwise assume.
  - The reason also rides along on the ntfy push, so the phone says what happened rather than just that something did.
- **A bounded project-state brief replaces the per-block re-read of `work_log.md` (`--brief`, on by default).** A project's `CLAUDE.md` typically tells every agent to read the work log before substantial work. That is sound advice for one interactive session and ruinous for a queue: `sandglass execute` runs each block through a *cold* `claude -p`, so the mandate is re-paid in full, at full price, once per block — against a file that only ever grows. Measured on a real project: a 313 KB work log plus an 85 KB system map is ~100k tokens of mandated reading before a block does any work of its own, on top of a ~24k fixed prefix. Sandglass now assembles the last two work-log entries plus `Progress.md` into a `<project_state>` block, prepends it to each prompt, and explicitly tells the run not to open those files in full. The brief has a hard 6,000-character cap — an uncapped brief is the original problem wearing a different hat. No-op in projects without a `master_plan/` directory, and skipped on a resumed prompt whose session already has it. New `sandglass/project_docs.py`; `--no-brief` restores the unbounded read.
- **`sandglass update` — self-update from the git repository.** Detects how Sandglass got onto the machine and does the right thing for that shape, because "update" means two different things: an **editable clone** (`pip install -e`, `pipx install -e`) *is* the working tree, so the update is `git pull` and nothing needs reinstalling; a **copy install** is a snapshot, so the update is a reinstall from the remote via pipx, uv or pip as appropriate. `--check` reports without changing anything and lists the incoming commits.
  - **It refuses to pull over uncommitted work.** A clone is somebody's working tree, and a pull across half a feature is how an afternoon disappears. `--force` skips the check but still never discards: the pull is `--ff-only`, there is no `reset --hard` anywhere in the module, and git refuses on conflict.
  - ⚠️ **It never resolves `sandglass` from PyPI.** That name belongs to an unrelated project there (0.0.1), and this tool has never been published — a plain `pip install --upgrade sandglass` would silently replace Sandglass with a stranger's package. Every install path is pinned to the full `git+https://…#subdirectory=sandglass-cli` URL, and a test asserts the bare name is never used as an install target.
- **`sandglass rotate-logs`** — archives all but the last N entries of `work_log.md` and `prompt_history.md` into `master_plan/archive/`, leaving a pointer line in the live file. The brief above stops the growth from being *re-read*; this stops it from accumulating in the first place. Nothing is deleted — history has to stay findable, so this is a move, and the pointer is what makes it one.
- **`sandglass queue lint`** — free static pre-flight over queued blocks: missing referenced paths, empty blocks, invalid effort values. A block that refuses because its dependency doesn't exist still burns a full prompt's worth of quota and delivers nothing (four such refusals in one recent batch cost ~20,900 recorded tokens and produced no code), so a second of grep beforehand is worth a lot. Read-only: linting an unimported markdown queue leaves the queue exactly as it found it.
- **Per-prompt `effort:` front matter, and `TIER:` markers are finally honoured.** Blocks could already set `model:`; they can now set `effort:` (`low`…`max`) on the next line. Separately, queue files in the wild already annotate blocks `**TIER: SONNET**` / `**TIER: CHEAP — EXTERNAL-OK**` — the author stating how much model the block deserves — and Sandglass was ignoring all of it and running every block on the default (Opus). Reading them is a fix, not a new convention: the intent was already written down. Precedence is explicit argument → front matter → tier marker, the resolved values show in `queue add`/`queue list`, and `--no-tiers` opts out.
- **`--budget-usd`** passes a hard per-prompt spend cap through to `claude --max-budget-usd`, so a runaway prompt stops at a number you chose instead of one you discover afterwards.

- **`sandglass sleeptime` — quiet hours for push notifications, on by default (22:00–06:00).** Sandglass is built to run unattended for hours, so a quota wait routinely spans the night; every ntfy notification is a phone buzzing at 3am about something you can't act on until morning. Inside the window every notification is dropped — *not* queued for later, since by morning the batch has moved on and a backlog of stale 3am alerts is worse than no alert at all. The run itself is untouched: it keeps waiting and resuming exactly as before. `sandglass sleeptime` shows the window (and whether it's active right now), `sandglass sleeptime 22 6` sets it (bare hours or `22:30`), `--off`/`--on` toggle it without losing the window. Enforced inside `notify.send()` rather than at each call site, so every notification obeys it by construction, including any added later.
- **Quiet hours are stored globally, in `~/.sandglass/settings.json`** — the first setting that isn't per-directory. `queue_source` describes a *project*, so it belongs in the local `.sandglass/`; sleep hours describe the *person*, and are the same whichever directory a run was launched from. Making them per-project would guarantee that the one run that wakes you is the one in the directory you forgot to configure. `SANDGLASS_QUIET_HOURS` (`"22:00-06:00"`, or `"off"`) overrides the file, matching how the ntfy topic itself is configured, so a headless/CI run can opt out without a home directory to write to. New `sandglass/quiet_hours.py`.
### Changed

- **A queue now runs as one warm session instead of N cold starts (`--session-mode chain`, the new default).** This is the largest saving in the release and the one the others were groundwork for. Every block used to run under `--no-session-persistence`: a brand-new conversation that re-paid the system prompt, the tool schemas, the project's `CLAUDE.md` and every file an earlier block had already read and understood — measured at ~24k tokens of fixed prefix plus ~100k of mandated reading, per block, before any block did work of its own. Chained, the queue pays that once; every later block rejoins the same conversation and reads the prefix back from cache at a fraction of base price. Unattended behaviour is unchanged in every other respect — blocks still run strictly one after another, auto-resume through quota hits, and cut themselves from the source file on completion.
  - **Blocks still read as separate tasks.** Each warm block is prefixed with a ~40-token turn separator ("the previous task is finished; this is a new, independent task; don't resume earlier work unless asked"). Without it a model reads block 2 as a continuation of block 1; with it, separation costs 40 tokens instead of the several thousand a cold start needs to achieve the same thing.
  - **The project brief is sent once, not per block** — a warm session already has it in history.
  - **A quota hit stays warm.** The chained session id lives in `.sandglass/run_state.json`, not in memory, precisely because the thing it must survive is the process ending: a run resumed hours later rejoins the same conversation rather than re-deriving what the interrupted block already worked out. This also removes the artifact-gate false positive — a resumed run knows which files it already wrote, so it finishes the remaining steps instead of concluding "already done", writing nothing, and tripping the gate.
  - **The chain ends when the drain does.** Cleared on a clean finish and on `queue clear`, and never rejoined after 24 hours, so an unrelated batch tomorrow doesn't get appended to today's conversation.
  - **Escape hatches, because chaining does trade isolation for cost.** `isolate: true` in a block's front matter runs that one block in a throwaway session and the chain resumes after it — for a review that shouldn't see the author's own reasoning, or a genuine second opinion. `--session-mode prompt` gives every block its own session (retries still resume; blocks never see each other), and `--session-mode isolate` restores the old fully cold behaviour.
- **The cached prompt prefix is kept stable between blocks (`--stable-prefix`, on by default).** `claude` bakes per-machine facts into the system prompt, including **git status** — which changes every time a prompt writes a file, shifting the prefix and forcing the whole cached span after it to be re-created rather than read. Cache creation is billed at a multiple of base rate and a cache read at a fraction of it, so this was a recurring premium paid for a prefix that was never reused: two byte-identical back-to-back runs both showed ~11.2k tokens of *creation* and zero incremental reuse. `--exclude-dynamic-system-prompt-sections` moves those sections into the first user message instead; the same facts still reach the model, just later in the prompt.
- **`execute` prints cost and the cache read/write split**, not just a token count. The split is the number worth watching: a run that is mostly cache *writes* is re-creating a prefix it never gets to reuse.
- **A quota hit now pushes an explicit "Token limits hit" notification, and does so on every path.** It's sent from the point of detection in `execute_queue` rather than from the auto-resume loop, so `sandglass execute --once` — which stops on a quota hit and never reaches that loop — now notifies too, where before it went silent. The message names the expected refresh time in **local wall-clock time** (`03:15`) instead of a UTC ISO timestamp, since it's read off a phone at a glance. The auto-resume loop's old "waiting for quota to refresh" push was removed rather than retitled: it fired a second after this one for the same event, and two pushes per quota hit is just noise.

- `ANTHROPIC_API_KEY` is no longer required or read directly by QuotaShield. `quotashield execute` now prints which account/plan will be used before running.
- Added `--permission-mode` on `execute`, since unattended queued prompts can't answer an interactive tool-permission prompt; defaults to `default` (same rules an interactive session would use), with a printed warning if a looser mode is chosen.
- Removed the `anthropic` SDK dependency entirely (`requirements.txt`, `setup.py`).
- Progress display switched from a fake percentage bar (based on a `max_tokens` budget the CLI backend doesn't expose) to a live streamed-character count with an elapsed-time spinner.
- Discovered the CLI backend emits `rate_limit_event`s with real quota status and a `resetsAt` timestamp during execution — a better foundation for the Phase 2 auto-resume feature than anything the API-based approach could have offered.

## [0.1.0] - 2026-07-21

### Features

- Queue management: `queue add` (text/file), `queue list`, `queue remove`, `queue clear`, `queue stats`
- Sequential prompt execution against the Claude API (`execute`, `execute --dry-run`)
- Live progress display (streamed characters, elapsed time)
- Response saving to `.quotashield/responses/response_<id>.json`
- Completed-prompt archive in `.quotashield/history.json`, browsable via `history`, `responses list`, `responses show`
- Atomic, corruption-resistant local JSON storage (no cloud, no database)
- Graceful handling of missing API keys, rate limits, and file errors — a failed run leaves the remaining queue intact for a later retry

### Known limitations

- No auto-polling — execution is manual only (`quotashield execute`)
- No graceful pause/auto-resume on quota hit (the run stops; retry later) — planned for Phase 2
- No background execution — runs in the foreground
- No response export (Markdown/CSV) — planned for Phase 2
